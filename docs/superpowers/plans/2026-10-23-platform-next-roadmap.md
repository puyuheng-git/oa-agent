## 0. 范围与硬约束（不可违反）

本路线图覆盖你提出的 5 点，并扩展「你可能没想到但迟早会撞上」的问题。它们是 **5 个可独立交付的子系统**，不要一次开一个巨型 PR。

| # | 子系统 | 一句话 |
|---|--------|--------|
| A | 员工背景与记忆文件 | 登录后注入「人是谁、偏好与长期记忆」，不是业务库直查 |
| B | 主 Agent 调度 + 多 Agent | 财务→财务 Agent 等分发与协作 |
| C | MCP / Skill / Tool 职责与可见权限 | 在「问一句 → 调 OA 接口」现实下划清边界与授权 |
| D | 固定 Workflow | 固定流程走确定性图，不靠模型自由发挥 |
| E | 历史会话持久化 | 员工下次登录还能看到并续聊以前的会话 |

**硬约束（现网设计已锁定）：**

1. 与 OA 只走 HTTP；对 `td_oa` **零访问**。背景信息只能来自 office-api（员工 token）或 Agent 自管库。
2. LangGraph 只做编排；**业务授权、校验、幂等在 office-api / Service**；模型输出不参与权限判定。
3. 管理员与员工两套主体；后台不能直改 Checkpoint / 图状态。
4. 密钥只写不读；不伪造指标；不展示隐藏推理链。
5. 管理写 = 权限点 + CSRF + `Idempotency-Key` + 审计。

**现状锚点（避免重复造轮）：**

- 对话原文已在 `agent_conversation_message`（管理员可查/导出）；员工端每次 `launch` **新建** `thread_id`，ticket 只在内存，故「感觉历史全丢」。
- 会话内多轮：`Checkpoint.history` + `memory` 压缩（截断/摘要/要点）已有。
- Tool / Skill 后台配置 + 启停已有；「MCP」在代码里主要是 Registry/Executor 命名，**不是**标准 MCP 协议服务端。
- 单一图 `travel_query`；发布配置已版本化。
- 接线设计把「多会话 `/v1/chat/threads*`」明确列为 **C 类未做**。

## 1. 推荐分期（建议你先拍这个总序）

### 推荐顺序：E → C → A → D → B

| 阶段 | 做什么 | 为什么先做 |

## 2. 子系统 E — 历史会话记忆（员工可见）

### 2.1 问题根因

- 消息已落库，但 **没有员工侧的「会话（thread）实体」API**。
- 每次 `redeem_launch` 都 `new_thread_id()`，前端也无侧栏拉历史。
- Checkpoint 绑 `thread_id`：旧线程不恢复则图内 `history/memory` 也断。

### 2.2 目标能力

1. 登录后看到本人会话列表（标题、更新时间、渠道、是否有未读/等待人工）。
2. 点开某会话 → 拉消息时间线 → 继续提问（复用同一 `thread_id` + Checkpointer）。
3. 新建会话、重命名、归档/删除（软删）、搜索（可选）。
4. 企微与 iframe **是否共用线程空间**要明确（见决断）。

### 2.3 建议数据模型

新建（或等价）：

- `agent_chat_thread`：`thread_id`, `tenant_id`, `oa`, `channel`, `title`, `status(active|archived|deleted)`, `created_at`, `updated_at`, `last_message_at`, `pinned`, `metadata_json`
- 已有 `agent_conversation_message` 继续挂 `thread_id`；打开会话时按时间翻页。
- 可选：`agent_chat_thread_summary`（列表摘要，避免每次扫全表拼标题）。

**标题策略（扩展想法）：**

- 首条用户消息截断；或模型生成短标题（异步，失败则截断）。
- 管理员导出仍走现有 conversations，不混员工删除语义。

### 2.4 API 草案（员工）

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/v1/chat/threads` | 本人列表，分页；`status` 过滤 |
| POST | `/v1/chat/threads` | 新建空会话，返回 `thread_id` |
| GET | `/v1/chat/threads/{id}/messages` | 历史消息（仅本人） |
| PATCH | `/v1/chat/threads/{id}` | 改标题 / 归档 |
| DELETE | `/v1/chat/threads/{id}` | 软删；硬删策略另定 |
| POST | `/v1/chat/session` | 增加可选 `thread_id`：续聊指定线程；缺省则新建 |

安全：一切按 session.`oa` 过滤；**禁止**用客户端自报 oa；管理端仍不能改 Checkpoint。

### 2.5 前端

- Chat 侧栏：会话列表 + 当前会话；ticket 刷新不丢当前 `thread_id`。
- 打开旧会话：先拉 messages 渲染，再发新消息走 stream（同一 thread）。
- 等待人工的会话：列表角标 + 进入后继续 poll run。

### 2.6 扩展想法（可选）

- **跨渠道合并：** 同 oa 在企微与网页看到同一列表，或分栏「网页 / 企微」。
- **「继续上次」：** 登录后默认打开最近活跃线程，而不是空白欢迎页。
- **合规：** 员工软删 ≠ 管理员审计消失；保留「对员工不可见、对审计可见」策略。
- **保留策略：** 按天/条数清理归档会话；与事件保留天数配置对齐。
- **分享/导出本人记录：** 员工导出自己的 JSON（低优先级）。

### 【决断 D2】会话身份范围

- **A.** 按 `oa` 全局一套会话（iframe + 企微共用）  
- **B.** 按 `(oa, channel)` 隔离  
- **C.** 按 `(oa, channel, device/client)` 更细隔离  

### 【决断 D3】打开助手默认行为

- **A.** 总是进入「新会话」欢迎页，历史在侧栏  
- **B.** 自动进入最近未归档会话  
- **C.** 由 OA 宿主页参数决定（`?thread=` / `?fresh=1`）  

### 【决断 D4】员工删除的语义

- **A.** 仅对自己隐藏（审计/训练库仍在）  
- **B.** 连同消息对员工与常规后台对话页不可见，审计摘要仍在  
- **C.** 真正物理删除（一般不推荐）

## 3. 子系统 C — MCP / Skill / Tool 职责与可见权限

### 3.1 结合现状的职责划分（建议定稿用语）

当前真实路径是：**员工自然语言 →（Skill 约束下的）模型选 Tool → Executor 调 office-api**。  
建议把三层说成人话，避免「MCP」一词 internally 混淆：

| 概念 | 建议职责 | 类比 | 现状 |
|------|----------|------|------|
| **Tool** | 一个具体、可调用的 office-api 能力（现多为 GET 只读）：路径、参数 schema、返回白名单、超时、上游 | 「螺丝刀」 | 已有，后台 CRUD |
| **Skill** | 面向一类员工问题的能力包：说明、示例、允许使用的 Tool 集合、填参指引、可选专属提示词 | 「工具箱 + 说明书」 | 已有；运行时按启用 Skill 过滤 Tool |
| **MCP（建议收窄）** | **连接与执行平面**：如何把 Tool 接到上游、校验参数、注入身份、记事件、限流；可含「外部 MCP Server 适配器」将来扩展 | 「车间与安规」 | 代码里叫 mcp 包，实为 Registry/Executor |

**不要让模型/员工直接「看见 MCP」**；员工只看见 Skill（能力），管理员看见 Tool + Skill +（可选）MCP 连接配置。

### 3.2 扩展：第四层你可能需要 —— **Agent / Domain**

多 Agent 时建议增加显式层（可与 Skill 组合）：

| 层 | 职责 |
|----|------|
| **Domain Agent** | 财务 / 人事 / 行政…：系统提示、可用 Skill 集合、可用固定 Workflow、模型、护栏 |
| **Orchestrator（主 Agent）** | 只做路由、澄清、汇总；默认不直接调业务 Tool（或只调极少数「元工具」） |

Skill 继续是「能力包」；Domain Agent 是「岗位角色」。一个 Skill 可挂到多个 Domain（或禁止，见决断）。

### 3.3 可见权限模型（对员工）

**原则：权限源在 OA / office-api，Agent 只做「可见性裁剪」，不做业务放行。**

建议两级：

1. **目录可见性（Agent 侧）**  
   - Skill / Tool / Domain Agent / Workflow 可配置：全员 / 角色标签 / OA 部门或职级声明（声明须来自 office-api 画像，不能来自模型） / 显式 oa 白名单。  
   - 不可见 = 提示词不出现、欢迎页不展示、模型选了也执行失败（`TOOL_NOT_AVAILABLE`）。

2. **数据权限（office-api 侧）**  
   - 即使 Skill 可见，接口仍只返回该员工 token 有权看的数据。  
   - Agent **绝不**因「Skill 对 TA 可见」而放宽 office-api 校验。

**扩展想法：**

- **场景开关：** 「报销季」临时对某 Skill 全员可见，过期自动关。  
- **风险等级：** Tool 已有 risk；对员工可见的仅 `low`；`high` 只走固定 Workflow + 确认。  
- **发现性 vs 可调用：** 「能在帮助里看到说明」≠「能被模型选中调用」（只读目录权限）。  
- **负向权限：** 某员工禁用某 Skill（投诉/误用）。  
- **审计：** 「谁在何时对谁开放了 Skill」记 `setting`/`catalog` 审计。

### 3.4 若引入标准 MCP 协议（可选远期）

- **入站：** 外部 MCP Client 调我们 —— 一般不需要（员工入口是 Chat/企微）。  
- **出站：** Agent 作为 Client 连公司内部 MCP Server（非 office-api 的知识库/日历等）—— 与「只走 HTTP 契约」可并存，但须：地址白名单、身份仍用员工 token 或服务账号分域、结果进白名单后再给模型。  
- **短期建议：** 先把职责文档和权限模型做对，**不**急着上标准 MCP 协议。

### 【决断 D5】「MCP」一词在本项目的官方含义

- **A.** 仅指内部执行平面（Registry/Executor），对外文档改称「执行器 / 连接器」，避免 MCP 协议联想  
- **B.** 保留 MCP 名，并规划兼容标准 MCP Client（出站）  
- **C.** 同时做协议兼容（入站+出站）——范围最大  

### 【决断 D6】员工可见权限的主数据来源

- **A.** 仅管理员在 Agent 后台配白名单 / 标签（简单，与 OA 组织不同步）  
- **B.** 登录时从 office-api 拉「可办事宜/角色」再映射到 Skill（准，需 OA 接口）  
- **C.** A+B 混合：后台默认规则 + OA 标签覆盖  

### 【决断 D7】模型选了不可见 Tool 时的行为

- **A.** 静默当不存在，回退帮助/澄清  
- **B.** 明确告知「该功能未对你开放」  
- **C.** 记安全事件并告警（高频探测）

## 4. 子系统 A — 员工背景信息与记忆文件

### 4.1 拆成两类「记忆」（建议）

| 类型 | 内容 | 来源 | 注入方式 | 生命周期 |
|------|------|------|----------|----------|
| **Profile（背景）** | 姓名、部门、岗位、直属上级、常用公司主体… | office-api（员工 token） | 登录/会话建立时拉一次，TTL 缓存 | 随人事变动失效 |
| **Memory file（长期记忆）** | 偏好（「我只关心九月」）、常用查询条件、昵称偏好、未完成待办摘要 | Agent 自管（从对话压缩/显式「请记住」写入） | 每次 understand 前装载 | 员工可查看/删除；可过期 |

**严禁：** 把工资、身份证、完整审批正文等敏感业务明细写入长期记忆；记忆只保留「摘要级」事实（与现有 history 摘要纪律一致）。

### 4.2 登录时序（建议）

```
launch/session 成功
  → 并行：mint 已完成的 token 拉 Profile（office-api）
  → 读 Memory store（按 oa）
  → 组装 ContextPack（有大小上限）
  → 本 thread 的 Checkpoint memory 仍管「会话内压缩」
  → ContextPack 注入系统提示独立区块，并标注「不是指令、可过时」
```

### 4.3 Memory 文件形态（扩展选项）

1. **结构化 JSON 要点**（与现有 `facts` 压缩同形）——推荐默认。  
2. **Markdown 日记**（按日追加）——可读性好，给模型噪声大。  
3. **分层：** `profile.md` + `preferences.json` + `open_loops.json`。  
4. **向量检索记忆**（远期）：只在记忆很长时上；一期不必上。

### 4.4 写入策略（扩展）

- **自动：** remember 节点除会话 memory 外，把「跨会话仍有价值」的要点晋升到长期记忆（需分类器或规则，防把一次性查询写进去）。  
- **显式：** 员工说「记住…」「以后别…」→ 专用意图写记忆。  
- **纠正：** 「忘掉上次说的偏好」→ 删除/作废条目。  
- **员工可见的「我的记忆」页：** 列表、编辑、清空（增强信任，GDPR 风格）。

### 4.5 与会话历史的关系

- Thread 历史 = 对话原文（E）。  
- Session memory = 单线程压缩（已有）。  
- Long-term memory = 跨线程（A）。  
三者不要合成一个大 blob，否则权限与清理会缠死。

### 【决断 D8】Profile 接口谁提供

- **A.** 现有 mint/用户信息已够用，Agent 只解析已有字段  
- **B.** OA 新增只读 `GET /agent/me/profile`（部门、岗位等）  
- **C.** 暂不做 Profile，只做长期记忆文件  

### 【决断 D9】长期记忆写入

- **A.** 仅显式「请记住」  
- **B.** 自动从压缩要点晋升（带白名单类型）  
- **C.** A+B

## 5. 子系统 D — 固定 Workflow

### 5.1 何时用固定 Workflow vs 自由 Agent

| 用固定 Workflow | 用自由对话 + Tool |
|-----------------|-------------------|
| 步骤稳定、合规要求高（报销提交、请假） | 探索性查询、闲聊、一次性问法 |
| 需要人工确认闸门、幂等键 | 只读查询、结果展示 |
| 要可审计的「走到了第几步」 | 单次问答 |

设计原文：「图形化编排不在本期」——这里的固定 Workflow 建议仍是 **代码/配置定义的 StateGraph**，不是拖拽 IDE；后台可选「选用哪张已发布图」。

### 5.2 形态建议

1. **注册表：** `workflow_id` → 编译好的图 + 入参 schema + 触发条件（Skill/意图/显式命令）。  
2. **触发：**  
   - 主 Agent 路由输出 `{"action":"workflow","workflow_id":"travel_reimburse_submit"}`；或  
   - 员工点「快捷流程」按钮（不经过模型）。  
3. **与发布配置：** 每个 Workflow 仍可有自己的 content_json 版本（已有 P5 机制可推广到多 workflow）。  
4. **混合：** Workflow 节点内仍可调 Tool；禁止节点内「再调另一个自由 Agent」除非明确设计（防循环）。

### 5.3 扩展想法

- **Workflow 模板库：** 查询类（已有 travel_query）、确认类（interrupt）、多步表单类（逐步问必填项）。  
- **补偿/回滚节点：** 写操作失败后的补偿（依赖 OA 幂等）。  
- **SLA 与超时：** 卡在某节点自动转人工。  
- **只读 Workflow：** 「月度报销核对清单」固定步骤但无写。  
- **A/B 发布：** 10% 流量走新图（高级，可后置）。

## 6. 子系统 B — 主 Agent 调度与多 Agent 协作

### 6.1 推荐架构（渐进，不要一上来 Mesh）

```
员工消息
  → Orchestrator（主 Agent）
       ├─ chat / 澄清
       ├─ 分发 → Domain Agent（财务/人事/…）→ Skill/Tool 或固定 Workflow
       └─（可选）并行多个 Domain 再汇总（二期）
```

**原则：**

- Orchestrator **默认不掌握全部 Tool 详情**，只掌握 Domain 目录与路由规则，降低提示词膨胀与误调。  
- Domain Agent 之间 **不直接聊天**；经 Orchestrator 或显式「handoff 状态」传递摘要（仍不含业务明细超标）。  
- 权限：员工不可见的 Domain 对 Orchestrator 也不可选。

### 6.2 三种实现档位

| 档位 | 做法 | 成本 | 风险 |
|------|------|------|------|
| **L1 逻辑多 Agent** | 同一进程多套提示词 + Skill 子集，仍一张或少数图 | 低 | 边界靠提示词 |
| **L2 图内分派** | Orchestrator 节点 → 子图 Domain | 中 | 状态/Checkpoint 设计要小心 |
| **L3 多服务** | 独立部署的 Agent 服务 | 高 | 超出当前单实例假设 |

**建议：先 L1，验证路由与权限，再 L2。**

### 6.3 协作模式（扩展）

1. **Handoff：** 财务 Agent 做完列表，把「记录 ID 摘要」交还 Orchestrator 展示。  
2. **Consultant：** Orchestrator 问人事 Agent「该员工请假余额口径」，只取结论句。  
3. **Supervisor：** 主 Agent 审 Domain 输出是否越权/编造后再发出（额外模型调用）。  
4. **澄清优先：** 路由不确定时先问员工「是报销还是考勤？」，不要猜错部门。

### 6.4 你可能没想到的坑

- **循环调用：** 财务↔人事互相 handoff → 要跳数上限与环检测。  
- **费用：** 每多一层 Agent 多一轮模型；需计入配置与监控。  
- **责任归属：** run 事件要记 `agent_id`（已有字段）/ `domain`，否则介入时不知道谁失败。  
- **版本绑定：** 子 Agent 配置变更不应影响进行中的 run（与 release 快照一致）。  
- **企微短窗口：** 多 Agent 更适合网页；企微要更短路径或只跑 L1。

## 7. 横切能力（五子系统都会用到）

| 能力 | 说明 |
|------|------|
| **ContextPack 预算** | Profile + 长期记忆 + 会话 memory + 历史轮次 + Skill 描述有总 Token 预算，可配置、可观测 |
| **统一审计字段** | `oa`, `thread_id`, `agent_id`, `domain`, `workflow_id`, `skill`, `tool` |
| **安全回归集** | 越权 Tool、伪造 oa、跨人 thread、记忆注入攻击（记忆里塞「忽略以上指令」） |
| **配置中心 vs 发布** | 权限标签、Domain 目录偏配置中心；路由策略/提示词偏发布版本 |
| **可观测** | 路由决策事件 `route_decision`（目标 Domain、置信度、是否澄清）——**不**记录思维链 |
| **降级** | 无模型时：固定 Workflow 快捷入口 + 规则路由仍可用 |
| **多实例** | 会话/记忆进 MySQL；Checkpoint 现状 SQLite 单实例——多 Agent 前评估迁移（设计 §15） |
